# Reporting Spec (Summary)

## Scope
Create a reporting capability that generates CI failure reports for:
1. Cilium OSS (`cilium/cilium`)
2. Tetragon OSS (`cilium/tetragon`)

## Data Sources
- OpenSearch indexes with ingested workflow, job, step, test suite, and test case data.
- Existing OSS ingestion uses:
  - Runs index: `runs-oss`
  - Rates index: `rates-oss`

## Report Requirements
For each product (one page per product):
- Per-workflow CI failures (branch-independent), ranked by number of hits.
  - Must aggregate unique `test_suite_name`, `test_case_owners`, and `test_suite_owners` across all failures for the workflow.
- Per workflow + branch CI failures, ranked by number of hits.
- Per workflow CI failures per branch (group failures).
- Failure grouping: `test_case_name` + normalized failure message (to group likely identical failures).
- Extract and display in all tables:
  - `test_case_name`
  - `test_suite_name`
  - `test_case_owners`
  - `test_suite_owners`
- Include up to 5 failure links per group, collapsed, and include both workflow and job links when available.
- Link labels must be `run#<run_id>` from the workflow run URL.
- Report header must include generation timestamp and total execution time (end-start).
- All tables must be placed inside a `<details>` section with caption text `Table`.

Time windows:
- 7, 14, 30, 60, 90 days (each section in the report).

Graphs:
- For each time window, include graphs for all branches.
- For each branch section, include branch-specific graphs.
- X axis must show dates, one point per day.
- Y axis must show failure counts.
- In each time window, include two bar charts inside the relevant subsections:
  - Per-workflow: runs vs failures per workflow (blue runs, red failures).
  - Per workflow + test: runs vs failures per workflow + test suite (blue runs, red failures).

Event filtering:
- Include only `schedule`, `push`, and `workflow_dispatch` events.

Failure definition:
- Count `failed` and `error` (workflows: `failure`; tests: `failed`/`error`).

## Report Structure
- Do not include a manual table of contents.
- Per time window:
  - Graphs for all branches.
  - Per-workflow CI failures.
  - Per workflow + branch CI failures.
  - One section per branch with branch-specific graphs.
    - Per-workflow CI failures (branch-scoped).
    - Per workflow CI failures (branch-scoped).
- Subsection headers should include the time window (and branch where applicable), e.g., "Branch X, last Y days".
- Trend analysis:
  - In the first time window (7 days), compare the current 7-day window to the previous 7-day window.
  - Include per-branch trend analyses for the same comparison.
  - Use emojis (green/orange/red) and include `workflow` names, `test` names, and `error` messages in backticks.

## Output Structure
- One report page per product.
- Landing page with links to the two product pages.
- All outputs should be generated by a new `report` subcommand; do not modify existing commands or workflows.

## Constraints
- Do not change existing code or workflows outside of adding the report subcommand and its supporting files.
- Reuse existing helper functions and packages only if they are not modified.
- Keep report logic separated from current ingestion logic.
